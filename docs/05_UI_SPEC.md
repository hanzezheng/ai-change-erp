# AI 农批经营助手 UI 设计规范

## 1. 文档目的

本文档定义 AI 农批经营助手移动端的最终 V1 UI 与交互规范。

本规范用于：

- Flutter 开发
- Cursor / Codex 实现
- 页面验收
- AI 与传统业务流程一致性检查

核心原则：

> 这是一个成熟的农批经营软件，AI 是其中更自然、更高效的一种操作方式。

没有 AI 时，所有核心经营流程仍必须完整可用。

------

# 2. 总体产品形态

产品不是：

- AI 聊天 App
- AI 语音录单 Demo
- ERPNext 手机后台
- CRM Dashboard
- PC ERP 缩小版

产品应该表现为：

> 高频、紧凑、清晰、可靠的移动经营工具。

主要业务对象：

- 首页
- 订单
- 客户
- 收款
- 商品
- 库存
- 更多

AI 不作为独立业务模块存在。

# 8. 首页

首页目标：

> 用户打开以后立刻知道今天发生了什么、什么需要处理、下一步能做什么。

推荐结构：

## 顶部

- 日期
- 用户/商户身份
- 通知入口

## 今日经营

使用压平的数据条，不使用多个独立 Dashboard 卡片。

例如：

今日订单 3单
待收款 2笔
已完成 1单

后续真实开发可以根据产品确认替换为：

今日销售额
订单数
当前应收

## 快捷操作

- 开订单
- 记收款
- 查客户
- 查库存

使用平铺入口，不使用大型卡片。

## 待处理

只展示真正需要动作的事项：

- 草稿待提交
- 信息待确认
- 收款待确认
- 明确 Reminder

“未收款”本身不是待处理任务。

## 最近订单

连续列表。

不使用每单一张卡片。

# 10. 订单状态与付款状态

必须分开。

## Order Status

正式 V1：

- 草稿
- 已提交
- 已完成
- 已取消

不要伪造订单「待确认」。ERPNext 没有对应的订单状态。

收款 Draft 的「待确认到账」是 Payment Confirmation Status，不是 Order Status。

## Pay Status

- 未收款
- 部分收款
- 已收款

禁止：

把“待收款”定义为订单状态。

禁止：

全额收款自动将订单变成已完成。

# 23. 订单提交校验

提交订单必须校验：

- customerId 存在
- 至少一个商品
- 每个商品有正式 itemCode
- qty > 0
- rate >= 0
- UOM 属于合法 allowedUoms

如果某一商品信息不完整：

不能静默删除。

必须阻止提交。

在对应商品行显示错误：

请填写数量

或：

请选择商品

## 保存草稿的校验（V1 已冻结）

编辑过程中允许字段未完整：这只是本地编辑状态，不产生 ERPNext 单据。

但点击「保存草稿」会创建 ERPNext Draft Sales Order，因此必须通过最低正式订单校验。

存在无效商品行时：

阻止保存，在对应商品行提示填写。

不静默删除该商品行，也不建立第二套订单草稿事实。

例如商品已选但数量为空：

提示「请填写数量」，而不是保存时把这一行丢掉。

# 28. 记录收款

Phase 4 V1 只支持：

关联一张已提交 Sales Order 的 Customer Receive。

记录收款入口优先从订单详情进入。

不实现 standalone customer payment。

收款页面必须支持：

- 客户（由关联订单带入，只读展示）
- 金额
- 收款方式（来自 `GET /api/v1/payment-methods`）
- 到账状态
- 关联订单

禁止正式 Payment 只保存一个自由输入客户姓名。

正式实现保存：

- customerId
- customerName
- relatedOrderId

备注暂不支持。后端正式支持前，UI 不展示备注输入框。

Phase 4 V1 只支持后端允许的同币种订单收款。Flutter 不自己计算汇率。

# 29. 收款方式

不要写死：

微信转账 / 现金 / 银行转账。

付款方式由：

```
GET /api/v1/payment-methods
```

动态返回当前 Company 真正可用的 ERPNext Mode of Payment。

未出现在该列表中的方式，UI 不得展示为可选项。

------

# 30. 到账状态

支持：

已到账
待确认

这是 Payment Confirmation Status，不是订单状态。

后端语义：

```
POST /payments
→ 创建待确认 Draft Payment Entry

POST /payments/{id}/confirm
→ 确认到账
```

Flutter 如果用户选择「待确认」：

只执行 `POST /payments`。

如果用户明确选择「已到账」：

可以顺序执行：

```
POST /payments
→ POST /payments/{id}/confirm
```

用户不需要再手动确认第二次。

如果第二步失败：

保留已经创建的 Draft Payment，
明确提示「收款已保存为待确认」。

不要创建第二张 Payment。

------

# 31. 收款累计逻辑

付款状态基于：

confirmedPaid =
该订单所有已到账 Payment 总额

remainingToCollect =
max(orderTotal - confirmedPaid, 0)

规则：

0：

未收款

0 < paid < total：

部分收款

paid >= total：

已收款

付款状态不改变 Order Status。

# 47. 移动端密度原则

目标不是极限压缩。

目标是：

高信息密度 + 易扫 + 易点。

商品允许：

1～2 行。

长名称允许自然占据空间。

禁止：

为了塞一行而使用极小字体。

禁止：

PC 表格缩小到手机。
